# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Pulsar Kids (pulsarkids.com; formerly WonderKids / ДивоСвіт — the folder, repo, Vercel project, localStorage key, database and the `wonderkids.secrets.v1` salt keep the old name, and the salt must never change) — a mobile-first learning playground for kids 3–10 (POC). Vite + React 18 + TypeScript frontend, plus Vercel serverless functions in `api/` backed by PostgreSQL. All UI copy and TTS text is Ukrainian; code and comments are English.

`README.md` still describes the app as "zero-backend, LocalStorage". That is outdated: game state lives on the server and only the auth session is kept in `localStorage` (`wonderkids-auth-v1`).

## Workspace layout

This repo is `app/` inside a non-git parent folder `WonderKids/` that holds sibling repos and shared files:

- `../scripts/` — dev / deploy helper scripts.
- `../docker-compose.yml` — local Postgres 16 on host port **54329**.
- `../doc/` — the original PRD, Tech Spec v2.1, PRD v4.0 (it wins over the older two where they disagree — e.g. v4.0 removed the parent's "minimum tasks per level" setting) and Tech Spec v6 (the language / logic / astronomy / art game pack). Code comments cite them (`PRD §4.1`, `FR-GAME-02`, `PRD v4.0 §2.3`, …).
- `../improvements/` — screenshot batches of requested UI changes (red marks on a screenshot = what to fix).

## Commands

```bash
npm run dev        # Vite on http://localhost:4321, bound to LAN; also serves /api from ./api
npm run build      # tsc -b && vite build — the only correctness check available
npm run preview    # serve dist/ on 4321
```

From the parent folder, `./scripts/dev.sh [port]` does the same as `npm run dev` (and installs deps if missing). `docker compose up -d db` starts a local Postgres on 54329, used only when `DATABASE_URL` is not set in `.env.local`.

```bash
npm test                 # node --test tests/*.test.* — pure logic: play-time rules, level engine, publish status
npm run check:content    # plays every game's generator at every path step and validates each task
node --test tests/engine.test.ts   # a single test file
```

- Tests run on plain Node (≥ 22.18 for `.ts` type-stripping), so anything they import must be free of React and `@/` imports — that is why `core/game/engine/*` and `core/game/templates/validate.ts` use relative `.ts` imports. `check:content` loads modules through Vite instead, so it can import anything; run it after touching any generator or content file.
- `npm run lint` does not work (ESLint is neither installed nor configured). `npm run build` is the type-check; `noUnusedLocals` / `noUnusedParameters` are on, so unused symbols fail the build.
- `./scripts/deploy-app.sh ["msg"]` builds, commits and pushes this repo — a push to `main` triggers the Vercel deploy (frontend + `api/`). `./scripts/autopush.sh` commits and pushes every workspace repo together. Both commit with a per-command identity (`git -c user.name/user.email`, see the scripts) and push straight to `main`; don't run them unless asked.
- Production health check: `curl https://pulsarkids.com/api/health`.

## Architecture

### Source layout (`src/`)

- `games/` — one folder per subject, every one laid out the same way: `index.ts` only registers the subject, `config.ts` holds `SUBJECT` and `GAMES` (the catalog cards — titles, steps, stars, intros; no task logic), `tasks.ts` holds the task generators as `TASKS` keyed by game id, and `content/` the raw data (words, flags, facts). `shared/` is the template-game toolkit; `defineSubject(SUBJECT, GAMES, TASKS)` joins the halves and throws at startup if a card has no tasks. **No subject brings screens of its own** — every game plays on the shared templates in `components/templates`. Math differs only in how tasks are made: random sums generated one at a time instead of a pool, so it registers with `defineGeneratedSubject` and keeps one generator per game in `generators/` (dispatched by `tasks.ts`).
- `core/` — logic with no screens, grouped by what it serves: `game/` (kernel contracts, level engine, template payloads, outro texts, the galaxy list), `child/` (the store, progress, the child's world, play time), `account/` (API client, auth, sync), `app/` (portal routing, SEO, UI prefs), plus `audio/`, `theme/`, `utils/`.
- `components/` — React building blocks by feature (`game`, `hub`, `templates`, `world`, `parent`, …).
- `pages/` — route screens by audience: `child/` (hub, game, world, vault, audio), `parent/`, `auth/` (parent login, child login, child picker), `admin/`.

### Micro-kernel plugins (`src/core/game/kernel`, `src/games`)

A subject is a `LearningModule` (`core/game/kernel/types.ts`): sub-categories (one per **game**), a pure `generateTask(config)`, a `GameView`, and optional `buildLevel`, `VisualHelper`, `getIntro`, `getHintSpeech`. Modules self-register with `moduleRegistry` at import time; `src/games/index.ts` (one sub-folder per subject, each holding that subject's games) is the barrel imported by `main.tsx`. Core, Hub and the game shell must stay subject-agnostic.

`src/core/game/galaxies.ts` is the Hub's subject list ("galaxies"); a galaxy is live when its `moduleId` points at a registered module, otherwise it renders as "coming soon".

Each `SubCategory` carries the declarative game config from PRD v4.0 §1.2 (`gameId`, `difficulty` 1–3 stars, `publishDate`, `tasksPerLevel`, `mechanics`, `hintDelaySec`, `hasText`, `progression`); `core/game/kernel/gameConfig.ts` converts it to the PRD's wire shape (`toGameConfig`) so the catalog can move to a CMS/DB later. The hub's star filter (`core/app/ui/useHubState`, kept in sessionStorage together with the selected galaxy) sorts and dims — it never hides a game. Card status is derived from `publishDate` only (`core/game/engine/publish.ts`): before it → locked «Скоро»; for 60 days after → "NEW" badge.

Two words that are easy to confuse:

- **`steps`** — length of a game's *path* (the Duolingo-style ladder in «Мій шлях»). The current path step is the difficulty coefficient passed as `TaskConfig.step`.
- **`tasksPerLevel`** — how many tasks one play session ("level") asks. PRD v4.0 calls these "steps" (`steps_count_default`). **Required in every game's config** (5–10): 10 for a quick tap-the-answer path game, 6 for free play, 5 where one task is long (the number maze). A new game must decide this for itself — there is no default.

**Story problems and riddles are frame × skin.** «Задачі» (`games/math/generators/wordProblems.ts`) and «Логічні задачі» (`games/logic/content/riddles.ts`) do not list their problems: a FRAME is what happens with the numbers or the clues (two heaps are joined; who is the tallest of three), a SKIN is who, where and what it is told about; a frame with a skin is one *kind*, and its names and numbers change on every draw. The path opens a fixed number of new kinds a step (five of 250, three of 150), band after band of rising difficulty. To add problems, add a skin to a frame's list or a frame to a band — and print the texts to read them.

**Spaced recall** (`core/game/engine/recall.ts`, written up for content authors in `docs/level-design.md` — read it before adding a game): a path level is five tasks new at the current step plus five recalled from the previous five steps, alternating. `composeLevel` does the split; generated games (math) get it in `drawCandidates`, template games through `recallLevel` (new/recalled worked out from how `pool(step)` grows), and ranked content (flags, famous people) composes its own `level` with `introSteps`.

Two kinds of games (`SubCategory.progression`):

- **`path`** (default) — every next step is harder; the card opens the path modal.
- **`free`** — content with no difficulty to grow (sorting rubbish, feeding dinosaurs, the 100 random tasks of «Часова Машина» in `games/history/content/timeMachine.ts`). Its card shows how many tasks exist (`LearningModule.taskCount`). No ladder, no step gifts/chests: the card starts play directly, all content is in the pool, unlimited replays. `subSteps()` returns 1 for these.

**The Language galaxy** (`games/language`, Tech Spec v6 §2.1) is one set of five game mechanics (`tasks.ts`) instantiated per `LangPack` — `content/uk.ts` and `content/en.ts` (`content/assoc.ts` holds the word pairs both share) — so the Ukrainian and English versions cannot drift apart; adding a language is adding a pack to `content/` and listing it in `PACKS` in `config.ts`. The step on which each stage of a game begins is `STAGE` in `tasks.ts`; `config.ts` reads it to introduce the stage. Every game has 50 steps, each opening up to 25 new questions (`PER_STEP` / `opened` — fewer where a word list is shorter); a level still asks 5 new + 5 recalled (`recallLevel`), so a replayed level rarely repeats itself. «Абетка» (`Mechanics.LetterGrid`) has no word list at all: its tables are made up by a seeded generator (`alphabetTables`) so that a step always opens the same ones — ten letters with a pale copy in each empty cell → no pale letters → eighteen letters → two swapped letters to find → the whole alphabet, emptier every step. Each pack carries a `flag` and `name`, which become the game's `SubCategory.group`: a galaxy whose games have two or more groups gets a chip filter in the hub (`GroupFilter`, kept per galaxy in `useHubState`) that — unlike the star filter — hides the other groups. Sentences are not written out: `content/uk.ts` builds them with the phrase engine (who × what they do × present / past / future, the verb agreeing in gender). English cards carry `Card.lang: 'en'`: the speaker reads them with an English voice (`speechEngine.speak(text, onEnd, lang)`, `POST /api/tts { lang: 'en' }`), while prompts, hints and facts stay Ukrainian and deliberately contain no English words — the Ukrainian voice would mispronounce them.

### Engine layer vs presentation layer (PRD v4.0 §3)

- **Engine** — `core/game/engine/BaseGameEngine.ts` (abstract, as specified) and `LevelEngine.ts` own one level's task queue. Rules: candidates are de-duplicated by `task.key` (falls back to `prompt`), so a level shrinks on its own when a game has fewer unique tasks than `tasksPerLevel`; a task the child gets wrong is queued **once more** at the end of the level and never shown a third time; blind guessing (3+ wrong taps on one task) appends a fresh task, and so does idling — every whole step the companion rolls back (`useIdleRollback`) becomes one more task and the companion stays where it rolled to; both share the `MAX_EXTRA_TASKS` cap. Levels are always dynamic — the old parent setting (`gameMode`) is gone from the UI and ignored. `task.key` must identify the *question*, not its dressing: two tasks a child would call "the same" need the same key (e.g. 1/2 of a pizza and 1/2 of a cake).
- **React binding** — `components/game/useGameSession.ts` builds the engine per level (via `module.buildLevel` or repeated `generateTask`) and exposes it to `GameScreen`. Modules never touch the store; views only call `callbacks.onSuccess / onMistake / speakPrompt`. `GameScreen` keys the view by queue position, so the repeat of a task is a fresh mount.
- **Presentation** — `components/templates/*`: the CORE UI templates (`GridChoiceLayout`, `DragMatchLayout`, `SequenceLayout`, `InteractiveMapLayout`, `PhysicsScaleLayout`, `SorterBinsLayout`, plus `CashTrayLayout`, `TangramLayout`, `GridAreaLayout`, `NumberMazeLayout`, `BubblePopLayout`, `DotToDotLayout`, `ColorMixLayout`, `LetterGridLayout`). They render a declarative `TemplatePayload` (`core/game/templates/types.ts`) through `TemplateGameView`; pure answer checks live in `core/game/templates/validate.ts`. All dragging goes through `useDragDrop` (drag **or** tap-item-then-tap-target; targets are `data-drop` elements).

A template-based subject is pure data: `games/shared/templateModule.ts` → `defineSubject(SUBJECT, GAMES, TASKS)`, where each game supplies `pool(step)` returning every task it can ask at that step (see `games/geography`, `ecology`, `history`). A game may also supply `level(step, count)` to compose a level itself — the flag game does: `geography/content/countries.ts` lists all countries ordered by how familiar their flag is, each path step introduces the next five and recalls five from the previous five steps. A `SequencePayload` may bring a `guide` — the whole row its cards are a part of (the Sun and all eight planets), shown as a strip below the board once the hint fires. A `DotToDotPayload` with `find` is «Знайди сузір’я»: no labels, the figure lost among other stars and only `ratio` times bigger than they are; the child slides a finger over its stars or taps them. On a `GridChoice` board whose task has an unknown drawn in it (`?` in a math line, ❓ in a story's picture row — `data-ask`) the right number flies into it. The number maze lights ONE next step when the hint fires and then steps aside until the child slips twice more. The till (`CashTrayLayout`) counts in the parent's currency: small values are round coins, the rest paper notes. Two optional pieces of a payload serve arithmetic: `counting` (tap-to-count cubes or rows of dots, shown by the shared `TemplateHelper` below the board when the hint fires — a task that has one keeps all its answers instead of narrowing to two) and `stimulus.pie` (a food cut into slices). A game's animated intro picture is data too: `SubCategory.demo`, drawn by `IntroDemo`.

Feedback is unified (PRD v4.0 §3.3): the engine's `AnswerResult` names a sound code (`SND_SUCCESS`, `SND_ERROR`, …), `useSound().playCode` maps it to the synthesiser, and views shake for 300 ms on a mistake.

- **Zero-aggression** is a product invariant: no fail states, no visible timers or countdowns, never the word "wrong". **Only mistakes raise a hint** — two on a task, or one on the repeat of a task missed earlier; never a pause, and a repeat starts as a normal task (its prompt is read out again). `hintActive` is then true and each template scaffolds itself (narrows choices, pulses the target, shows a counter).
- **How to answer is told once, not printed on every task.** The tap / drag / swap instruction is a first-run tip per board type (`components/coach/tips.ts`, `HOW_TO`), drag targets light up while a card hovers over them (`useDragDrop().over`), and when there is a single thing to place a tap on the target is enough (`soleItem`). Prompts must be explicit instructions a child can act on.
- **First-run tips** (`components/coach/CoachTips.tsx`): one at a time, each spotlighting a control via a `data-tip="…"` anchor and read aloud; it stays until the child closes it and never returns. Seen tips are `tip:<id>` keys in the child's `treasures` (so they sync with no schema change); the parent cabinet can reset them.
- **Never interrupt a level — but never start one on an empty tank.** A level that has not had its first answer yet goes straight to the rest screen when the gauge is empty (`outOfTime` in `GameScreen`, trusted only after the server answered — `screen.synced`); otherwise «Наступний рівень!» would keep play going for ever. Running out of play time mid-level only takes effect once the level in progress is finished (the server allows `DEPLETION_GRACE_MS` of overrun for that); while the rest screen is up nothing speaks or runs underneath.
- **Text and voice**: text cards and prompts get a tap-to-hear `SpeakButton` (hidden when the parent turns `settings.ttsButtons` off); games with `hasText` get the one-time tip pointing at them. `TaskInstance.outro` is a short fact spoken and shown after a correct answer — the level waits until it has been read to the end (`session.awaitingOutro` / `outroDone`), never a guessed delay. It should be a pool of texts (`string[]`, ten where the content allows; `core/game/content/outro.ts` rotates through it so a replay tells a new story; `check:content` rejects empty, repeated or broken texts). The speech engine silences itself when the page is hidden (phone locked, app switched).

### Screen time (server-authoritative)

The server owns the play-time budget (PRD v4.0 §2.2). `components/game/useScreenTime.ts` calls `POST /api/v1/session/start` when a game becomes active, `PUT /api/v1/session/heartbeat` every 30 s, and a final beat with `end: 'pause' | 'depleted'`; parents refill via `POST /api/v1/session/reset`. The rules are pure functions in `api/_lib/screenTime.js` (day roll-over in the child's time zone, a >90 s gap between beats counts as a pause, a break as long as the cooldown refills the session tank even if it never ran dry — `refillIfRested`, the daily cap still counts those minutes —, cooldown, daily cap → rest until local midnight, forced end after a grace period if the client never ends the session). `PUT /api/state` never writes `wk_screen_time`. The store's `screenTime` is only a local mirror that animates the gauge between beats (`applyServerScreenTime`); `core/child/time/screenTime.ts` turns it into the fuel percentage. The child sees a draining row of the theme's `timeToken` — an hourglass or time crystal, never a star (stars mean progress, difficulty and rewards only).

### The child's world (`src/core/child/world`, `/world`)

«Мій світ» replaced the old single "dream build". `world.ts` holds the rules (pure, tested):

- **The planet** — the child *exchanges* artifacts for items of the active theme: ten buildings (`BUILDING_COSTS`, the last is `theme.dreamBuild` and unlocks only when the other nine stand) and eight decorations (`DECOR_COSTS`), listed per theme in `themeWorlds.ts`. `artifacts` is never decremented: a purchase is remembered as a key `world:<themeId>:<itemId>` inside the child's `treasures` array (so it syncs with no schema change), and the balance is `earned − spent` (`balanceOf`). Every counter and the family goals show that balance — read it with `useBalance()`, never `s.artifacts` directly — so buying something for the planet genuinely sets the goals back: the child chooses between building and saving. An item's price depends only on its id (`b3`, `d5`), never on the theme. Buying goes through `store.buyWorldItem`, which re-checks the balance.
- **«Станції знань»** (replaced «Землі знань», where every game owned a landmark) — opened with a second currency, **keys of knowledge** («ключі знань» 🗝️). Keys are derived, not stored: one per path step passed for the first time in *any* game, plus the first `KEYS_PER_FREE_GAME` levels of a free-play game (`keysEarned`; `core/child/world/games.ts` reads them off the catalog — use `keysOf(progress, treasures)` for the balance). A key does not know which game it came from, so new games and galaxies only add ways to earn keys — **never tie anything in the world to a particular game again**. Stations are a fixed list of six per planet (`stations.ts`), 25 % dearer per planet (`stationCost`); an opened one is the key `know:p<N>:<id>` in `treasures` (no theme in it) and cannot be sold. `store.openStation` re-checks the balance.
- **Residents** — derived: every 5th path step is a gift that brings one (the theme's own ten, then the shared `VISITORS` list). This is a surprise by design: the UI never says when the next one comes, how many exist or who is next — only who has arrived.

Levels played are counted in `progress` under `${module}:${sub}#plays` (`core/child/progress/plays.ts`). Code that walks `progress` or `treasures` keys must expect these extra `#plays` / `world:` / `worldloss:` / `know:` / `tip:` entries.

`components/world/PlanetView.tsx` shows the planet as a globe (`Globe.tsx`) the child turns with a finger in every direction and zooms with two (`useGestures`; things are sized as a share of the planet's radius, so zooming in makes the small ones bigger). Every thing has a place in degrees, spread evenly over the whole globe (`places.ts`: a Fibonacci lattice — never a heap), `project` turns it into a screen position for the current yaw / pitch, and what is on the far side is simply not drawn. No 3D library and no zoom library — positions are plain maths. There are no «+» plots: what is not built yet is a dim outline. **Tapping anything — on the planet or in the list below, built or not — is the same action** (`select`): it reads out what the thing is, what it costs and how much is still missing, and offers the button to build (or sell) when that is possible. Choosing a thing glides the planet to it and raises a **bar fixed to the bottom of the screen** (never beside the planet, where it got lost): a message with a button (build, sell) stays until something else is chosen or it is closed; one without (still saving, locked) fades out by itself. Buying or selling cuts off whatever was being said about the price. Tapping a planet of the system strip shows that planet — a closed one too, dark under a lock, everything on it dimmed — and raises the sheet of what it asks for (pictures with numbers, not sentences; it is not printed on the page). ⛶ opens `SolarSystem.tsx`: the whole screen with the Sun and all eight planets going round it and nothing else; pinch or tap a planet to fly up to it and see what stands there. A tapped planet — open or not — tells a story about itself, read aloud and shown in a card at the bottom («Розкажи ще» tells the next): twenty per planet in `core/child/world/planetFacts.ts`, rotated with `pickOutro` so none repeats before all were told. The things on a planet not reached yet cannot be tapped there (`Globe` without `onTap`). It is for looking only.

**The world is a solar system** (`docs/world-roadmap.md` — read it before touching `core/child/world`): eight planets travelled from Neptune inwards, the goal is the Sun. Every planet has the same things to build (the theme's nine buildings, the spaceport `SPACEPORT_ID`, the dream build `DREAM_ID`, eight decorations), one level higher and 25 % dearer per planet (`itemCost(id, planet)`). Purchases on the first planet keep the old key `world:<theme>:<id>`; later ones are `world:<theme>:p<N>:<id>` (`ownedKey` / `parseOwned`). Which planet is open is derived, never stored: `planetNeeds` lists what a planet asks for (everything built, the spaceport, 60 % of its stations of knowledge open — `STATIONS_SHARE` —, residents, treasures) and `frontierPlanet` opens the next one. The planet under the buildings is `PlanetArt` of the real planet, turned by the same yaw.

The header has ONE door into «Мій світ» — the artifact purse. (A second badge showing the dream build used to open the same page.) Gifts («подарунки») are not a currency: every 5th path step is a gift that brings a resident to the world.

### Voice (`src/core/audio/SpeechEngine.ts`, `api/tts.js`)

Speech has two tiers. When Google Speech is in effect for the account (`features.cloudTts` in the `GET /api/state` response) the engine fetches each phrase from `POST /api/tts` — our proxy to Google Cloud TTS, which caches every phrase in `wk_tts_cache` — and plays it with an `<audio>` element. Keep it that way: on iOS the ring/silent switch mutes Web Audio (all our sound effects) but not `<audio>`, so speech routed through the `AudioContext` goes silent on a muted phone. Otherwise, and whenever the cloud is slow (3.5 s), offline or rejects the key, it falls back to the browser's Web Speech voice. Callers only ever use `speechEngine.speak / cancel`; `onEnd` fires exactly once on every path — finished, cut off by `cancel`/the next phrase, refused, or never started (3 s watchdog) — so UI that waits on it (the speaker halo, the level waiting for a fact) cannot get stuck. All cloud phrases play through one shared `<audio>` element unlocked on the first touch (iOS only autoplays an element a tap once started). A Google key never reaches a browser.

Keys live in `wk_tts_keys` (AES-GCM-encrypted, `api/_lib/secrets.js`), each with its own voice. Which key an account gets is decided in one place, `getTtsConfig` in `api/_lib/db.js`: the key assigned to the account (`wk_parents.tts_key_id`) wins; otherwise the single **global** key (`is_global`) applies; and `wk_parents.tts_off` switches the account off regardless. Saving a key as global clears the flag on any other; assigning a key to an account takes that account off whatever key it had (`saveTtsKey`).

### Admin area (`src/pages/admin/AdminPage.tsx`, `src/pages/admin/*`, `api/admin/*`)

`/admin/*` is lazy-loaded and not mounted on the `play.*` portal. `/admin/games` is a live summary of every game (kind, mechanics, path length, stars, tasks per level, how many different tasks overall and per step), computed in the browser from `moduleRegistry` — exact where a module implements `tasksAt` (all template modules), sampled from `generateTask` otherwise; nothing there is hand-maintained. `/admin` lists every parent account, their children and each child's progress per game, with a one-line Google Speech status and on/off switch per account. `/admin/speech` manages the keys: add or edit, choose who each one serves (global or selected accounts), test, delete, plus the same per-account switches. It authenticates with a shared `ADMIN_KEY` env var sent as `x-admin-key` — deliberately not with parent tokens, because parent login is email-only.

### Themes that reshape the UI

Most themes are a palette + emoji set. `lego` and `minecraft` also change shape: `styles/global.css` overrides the shared tokens under `:root[data-theme='…']` (radii, shadows, font), so every component follows without per-component rules, and `components/theme/ThemeDecor.tsx` draws their scenery and wordmark. New components should keep using `var(--radius*)` / `var(--shadow*)` rather than literals, or they will look out of place in those themes.

### State (`src/core/child/store/useGameStore.ts`)

One Zustand store. The persisted shape is only `{ children: ChildState[], activeChildId }` — a parent account holds several children. The active child's fields (`profile`, `themeId`, `settings`, `progress`, …) are **mirrored** onto the store root so components read `s.settings` directly; every mutation must go through `patchActive` / `commit` so `children[]` and the mirror stay consistent. `hydrate` → `fromPersisted` → `migrateChild` fills defaults for missing fields; a new field needs a default there.

### Sync and auth (`src/core/account/sync`, `core/account/auth`, `core/account/api`)

`useRemoteSync` loads `GET /api/state` after login (the app shows a splash until `ready`), then debounces `PUT /api/state` (700 ms) on every store change with the whole persistable state. The parent cabinet pauses auto-save via `useSyncControl` and persists on an explicit Save button.

Two login kinds, both yielding a JWT whose subject is the **parent account id**: parent = Auth0 (email only while Auth0 is not configured — see Accounts); child = nickname + PIN, token also carries `childId`, which is auto-selected after load.

### Portals and the public site (`src/core/app/portal.ts`)

One deployment, four faces chosen by hostname: the **root domain** → `site` (the public landing page); `parents.*` → parent cabinet (+ admin) only; `play.*` → child hub only, parent routes not mounted; localhost / LAN / `*.vercel.app` → `dev`, everything reachable on one origin. Routing in `App.tsx` branches on this, so route changes need checking against all of them. On `site` the SPA only redirects app paths to their subdomain (`portalUrl`). `VITE_USE_SUBDOMAINS=false` keeps the whole app on the root domain.

The landing page is **static HTML** (`landing.html`, a second Vite entry — no React), so crawlers get real content; `vercel.json` rewrites `/` to it on every host except `play.*` / `parents.*`. For that rewrite to apply, the Vercel build renames the app shell `index.html` → `app.html` (`seo-plugin.ts`, only when `VERCEL` is set): Vercel serves an existing file before rewrites, so an `index.html` in the output would take over `/`. The old `*.wonderkids.yluch.app` hosts 308-redirect to `pulsarkids.com` (`vercel.json`). Its copy states concrete numbers (games, flags, tasks) — keep them true when content changes.

### Analytics

Vercel Web Analytics (anonymous page views, no cookies) is on for the whole site: the app calls `inject()` from `@vercel/analytics` in `main.tsx` (query strings are cut off first — they can carry an Auth0 sign-in code), and the static landing page loads `/_vercel/insights/script.js` itself. `vercel.json`'s catch-all rewrite leaves `/_vercel/` alone for that. Numbers are in the Vercel dashboard → project → Analytics.

### SEO

- `seo-plugin.ts` (Vite) fills `__SITE_URL__` / `__PLAY_URL__` / `__PARENTS_URL__` in both HTML entries from `VITE_SITE_URL`, and emits `robots.txt` and `sitemap.xml`.
- `landing.html` carries the full set: title, description, canonical, hreflang, Open Graph / Twitter (`public/og-image.png`), and JSON-LD (`WebSite`, `WebApplication`). It is dressed in the palette of the game's `galaxy` theme (dark sky, stars, the Solar System in the hero) and has no FAQ section.
- The SPA is `noindex` by default; `core/app/seo/usePageMeta` sets title, description, robots and canonical per page, and only the two public login pages opt into `index`. `vercel.json` adds `X-Robots-Tag: noindex` on personal paths.

### Accounts

**Parent login goes through Auth0** once `VITE_AUTH0_DOMAIN` and `VITE_AUTH0_CLIENT_ID` are set (production: `auth.pulsarkids.com`, the custom domain of the project's own Auth0 tenant — tokens are issued and verified under that name, so the variable must be the custom domain, not the `*.auth0.com` one) (both public; the frontend and `api/` read the same two variables). `pages/auth/Auth0Login.tsx` (lazy — the SDK is not in the child's bundle) sends a parent without a session **straight** to Auth0 Universal Login (no button; it stops only on an Auth0 error or a refused account, where going again would loop) and back to `/parent-login`, then trades the Auth0 **ID token** for our own JWT at `POST /api/auth/login { idToken }` (`api/_lib/auth0.js` checks signature, issuer, audience). Auth0 only proves the mailbox: the account is still found by `email_key`, so everything downstream (child login, sync, tokens) is unchanged. The address must be `email_verified` — the email is the identity, so an unverified one would open someone else's account. A parent's logout also ends the Auth0 session (`auth0LogoutUrl`) and returns to the child login (`play.*` `/login`), not to the parent login, which would bounce back to Auth0. Every origin a parent signs in on needs `<origin>/parent-login` in the Auth0 application's callback URLs, and the child login (`https://play.pulsarkids.com/login`, `http://localhost:4321/login`) in its logout URLs.

Without those variables parent login is by email only (no password), and with them an email-only `POST /api/auth/login` answers 403 `auth0_required`. **One mailbox = one account**: `api/_lib/email.js` derives `email_key` (Gmail dots, `+tags` and `googlemail.com` collapse), unique in `wk_parents`. In the email-only mode signing in never creates an account: an unknown address answers `account_not_found` (with a `suggestion` for a mistyped domain) and the account is created only after the parent confirms (`create: true`). Look-alike accounts that are genuinely different addresses cannot be merged automatically — the admin page flags them and can delete an account.

### Themes (`src/core/theme`)

A theme is a deep skin (palette, mascot, goal, artifact, time token, chest, treasures), not just colours. `ThemeProvider` writes the palette to CSS custom properties on `:root`; components use CSS Modules and read only those variables. A child's `themeId` is `null` until chosen and resolves to the neutral `galaxy` theme.

### API (`api/`)

`api/*.js` are Vercel serverless functions and the **only** API implementation (`_`-prefixed files/folders are shared code, not routes). In dev there is no separate backend: the `devApi()` Vite plugin (`dev-api.ts`) mirrors Vercel's file-based routing and serves the same handlers in-process, loading them through Vite's SSR module graph so edits apply on the next request. Handlers must stay runtime-neutral: default-export `(req, res)`, do their own method checks, and use only `req.method / headers / query / body` and `res.status().json() / setHeader()` — anything else needs a matching shim in `dev-api.ts`. `vite preview` does not serve `/api`. **The Vercel Hobby plan allows 12 functions per deployment and `api/` has exactly 12** — a 13th endpoint file builds fine and then fails the deployment (`exceeded_serverless_functions_per_deployment`), so new behaviour goes into an existing endpoint (as the Auth0 login did) or `_lib/`.

Endpoints: `GET /api/health`, `POST /api/auth/login`, `POST /api/auth/child-login` (also, with a parent token and `{ childId }`, the cabinet's «Відкрити гру дитини»: a child token for one of the account's own children, handed to a new tab on the child portal as the URL fragment `#child=<token>` — `adoptChildHandoff` in `main.tsx`), `GET /api/nickname`, `GET|PUT /api/state`, and `POST /api/v1/session/start`, `PUT /api/v1/session/heartbeat`, `POST /api/v1/session/reset` (the last is parent-only; a child token always acts on its own profile, a parent token names one with `child_profile_id`). Also `POST /api/tts` and the admin endpoints `GET|PUT /api/admin/users`, `GET|POST|PUT|DELETE /api/admin/speech`, `POST /api/admin/tts-test`.

The client sends the save as one JSON object, but `api/_lib/db.js` decomposes it into normalised `wk_*` tables in `saveState` and reassembles it in `getState`. Adding a persisted field therefore touches the store types + `migrateChild` on the client, and the table DDL + `saveState` + `getState` in `db.js`. The schema is created idempotently (`ensureSchema`); there are no migrations, so column changes need an explicit `ALTER TABLE` in that block.

Env vars for `api/`: `DATABASE_URL`, `JWT_SECRET`, `ADMIN_KEY` (admin panel; ≥ 8 chars), optional `JWT_EXPIRES_IN`, `VITE_AUTH0_DOMAIN` + `VITE_AUTH0_CLIENT_ID` (parent login through Auth0; also needed at build time), `PGSSL`, `PGSSL_INSECURE`, `SECRETS_KEY` (encrypts stored Google keys; defaults to `JWT_SECRET` and must never change once keys are saved). Production values live in Vercel; locally they come from the gitignored `.env.local` (see `.env.example`). **`.env.local` currently points at the production (Neon) database**, so local dev reads and writes real data — don't run destructive queries, schema experiments or test logins that create junk accounts against it. Without `DATABASE_URL` the plugin falls back to the Docker database. To run against the Docker database while `.env.local` exists, set it in the shell, which wins over the file: `DATABASE_URL=postgres://wonderkids:wonderkids@localhost:54329/wonderkids PGSSL=false JWT_SECRET=dev npx vite`. `--mode test` does NOT help — Vite loads `.env.local` in every mode.

## Content rules (non-negotiable)

- **Money is never «гривня» in the code of a game.** The parent chooses the currency (`settings.currency`: hryvnia by default, euro, dollar, pound, złoty); the shell passes it to every generator as `TaskConfig.currency`, and `currencyOf(config.currency)` (`core/game/content/currency.ts`) gives its sign, its short form for a price tag, its count forms and gender (`counted`, for `num` / `countWord`), its small change (`minor`) and which values are coins. Every task that mentions money — the shop, the story problems, comparing measures, and anything added later — takes its words and signs from there: «Скільки ${money.counted[2]} здачі?», never a literal «гривень» or «грн». A template game's `pool(step, config)` gets the same `config`.

- **Nine answers — or six where a card is big; never four.** A tap-the-answer board (`Mechanics.GridChoice`) offers **nine** options in a 3×3 grid (`cols: 3`, `withDistractors(…, 9, …)`) when an answer is small: a number, a fraction (written with a slash — `1/5` — so nine fit a phone), a little figure. Where a card carries a picture, a name and a speaker (natural zones and their animals, dinosaurs, clocks, planets, story problems) the owner asked for **six**. The hint still narrows the board to two. Only the boards of portraits (famous people, inventors) and capitals still offer four.
- **Plenty of different tasks.** A path step opens ~25 new tasks, not 5 (`PER_STEP` in `games/logic/content/data.ts` and `games/language/tasks.ts`), and a content group (the shadow-lotto catalog, a word list) holds 100+ items, so the same task rarely comes round again.
- **Harder means more alike, not just more.** Difficulty of a recognition game grows by making the wrong answers resemble the right one: shadows of unrelated things → of one family (a dog and a horse) → of look-alikes (a dog, a wolf, a fox), with a softer shadow edge (`SHADOW_STEPS`); mirror halves that differ by many cells → by a single cell (`MIRROR_STEPS`).
- **Names of things are enums, not strings.** A board is `Mechanics.DragMatch` (`core/game/kernel/mechanics.ts`), in a game's card (`mechanics`) and in a task's payload (`template`) alike — never `'UI_DRAG_MATCH'`. Add a member there for a new board; give any new closed set of names an enum of its own.
- **Texts must read like a person wrote them.** Never glue a nominative onto a colon («Коли це буває: достигають кавуни?», «Знайди прапор: Україна»). A text with a variable goes through the phrase engine `core/lang/uk.ts` (`noun` / `verb` / `adj` → `inflect`, `conjugate`, `agree`, `counted`, `accusative`, `clause`, `phrase`), which puts the word in the right case, gender, number and tense: «Коли достигають кавуни?», «Знайди прапор України», «Куди викинути зубну щітку?», «Зібрано 6 цеглинок». Irregular forms are given with the word; `tests/lang.test.ts` covers the rules. After touching texts, read them: print a game's prompts and check each by ear.
- **Sentence-long answers are a list.** Nine answers still, but one to a row (`cols: 1`) when they are whole sentences — «Чому так?» does this, filling the board with right answers of other topics' questions of the same kind (`wrongAnswers` in `games/ecology/tasks.ts`).
- **What the voice says may differ from what is written.** `TaskInstance.speak` is the spoken form of a prompt; always read `spokenPrompt(task)`, never `task.prompt`, where the voice speaks. **The voice module is `core/lang/numbers.ts`, and everything spoken passes through it**: `speechEngine.speak` hands every Ukrainian phrase to `voiced()` before it sounds, so no game needs wiring and none can forget it. `voiced` turns whatever is still a digit into a word, reading its form off the neighbours — «2 машинки» → «дві машинки» (a short list of feminine and neuter words; the rest are masculine), «до 20 годин» → «до двадцяти годин», «3 з 4» → «три з чотирьох», «1846 року», «у 1991 році», «2011-го», «24 серпня», «12:00» → «дванадцята година», «о 7:00» → «о сьомій» — and says a letter named in a sentence by its name («на літеру „Л“» → «ел», «від И до П»). That is guessing from context, so **an author who knows the gender and the case says so**: `num(2, 'f')` is shown as «2» and said as «дві», `num(3, 'f', 'gen')` → «трьох», `say(shown, said)` does the same for anything else, `letterName('ж')` is «же»; a marked number is never touched by the guesser. Use the marks in every generated text (story problems, riddles, prices) — there the gender is known and the guess is not needed. `templateTask` splits a marked prompt into `prompt` / `speak` by itself; a fact is shown through `written()`; a generator that builds a task by hand does both (`prompt: written(text), speak: spoken(text)`). When a new word keeps being read with the wrong «два / дві» or «один / одна / одне», add it to `FEMININE` / `NEUTER` there; when a new pattern is misread, add a rule and a line to `tests/lang.test.ts`. A count that ends in one («21 цукерка») bends the whole sentence — story generators throw such a draw away.
- **Real people get real portraits, real things real pictures.** `public/people/<id>.webp` (people, inventors) and `public/things/<person id>.webp` / `public/things/inv_<invention id>.webp` (what a person is known for, an invention as it looked when it was made — Benz's 1886 motor car, not a toy-car emoji) — 224 px square WebPs of a few KB from Wikimedia Commons, shown through `Card.image` / `stimulus.image` (the emoji stays as the fallback). Every file is listed with its licence in the folder's `CREDITS.md`; add a row with every new picture. Only freely licensed files: a work still under copyright (Picasso, Prymachenko) keeps its pictogram, and so does anything no honest picture was found for (`PICTURED` in `games/history/content/data.ts` lists who has one).
- **The map is the real one.** `core/game/templates/worldMap.ts` holds real coastlines (Natural Earth 1:110m, merged by continent, simplified) on a 200×100 equirectangular canvas — never go back to blobs.
- **The rest screen never shows a number to wait for.** Its message is read out and says «Повернись за деякий час»; the real countdown is shown only to the parent (`ParentDashboard`).
- **No fun facts where there is nothing to tell.** The pure logic games (patterns, shadow lotto, mirror, riddles), the bubbles, the shop and the story problems have no `outro` — the next task starts at once. A parent can switch all facts off (`settings.funFacts`, «Цікаві факти» in the cabinet).
- **A fact belongs to its task.** What is told after an answer is about the very thing that was asked — this animal, this sea, this planet question — and is written with it in the content. Never pad a pool with facts of the whole category (`SOLAR_FACTS`, a language's general facts): the child joins the stars of «Стріла» and must not be told about the Milky Way. Where stories exist per material rather than per thing (sorting rubbish), they are dealt out one to a task.
- **Planets look like themselves and turn.** In «Парад Планет» a planet is `Card.planet` → `components/templates/PlanetArt.tsx`: a drawn surface (Mars with dark plains and polar caps, banded Jupiter with its red spot, ringed Saturn, Uranus on its side) sliding inside the disc, so it spins on its axis. Never a plain coloured ball or emoji.
- **A level of a slow game is five tasks.** The logic games (nine answers to study, several shadows to place) ask 5 per level, not 10 — `composeLevel` then gives 3 new + 2 recalled.
- **The win screen is read out** («Ти неймовірний! Зібрано 6 цеглинок. Усі 6 завдань виконано. Чудова робота!» — `theme.artifact.counted` holds the count forms); its buttons are not. Nothing about a task may sound under it.

## Conventions

- Import via the `@/` alias (→ `src/`).
- Styling: CSS Modules next to the component + theme CSS variables; no hard-coded theme colours.
- Mobile-first: touch targets ≥ 56px, safe-area insets, no double-tap zoom.
- Audio is synthesised (Web Audio in `core/audio/AudioEngine.ts`) and speech uses the Web Speech API; voiced text is gated per channel (`core/audio/voiceChannels.ts`).
